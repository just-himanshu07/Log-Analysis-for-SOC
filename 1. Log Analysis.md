# Introduction to Log Analysis

**Domain:** Cybersecurity | Security Operations Center (SOC)  
**Lab Type:** Hands-on Practical  
**Platform:** Windows 10/11 and Linux  
**Focus:** Log Sources, PowerShell Logging, and Event Investigation

---

## 🎯 Objective

Understand the fundamentals of log analysis, identify common Windows and Linux log sources, and investigate PowerShell activity using Windows Event Viewer.

---

## 1. What Is Log Analysis?

A **log** is a record of events generated by an operating system, application, service, or network device.

**Log analysis** involves examining these records to understand system activity, identify suspicious behavior, and investigate potential security incidents.

### Common Log Fields

| Field | Description |
|---|---|
| Timestamp | Date and time of the event |
| Event Source | Application, service, or system that generated the event |
| Event Description | Details of the recorded activity |
| Severity | Importance of the event, where applicable |
| Username | Account associated with the event, where available |
| Source IP | Originating IP address, where applicable |
| Process ID | Identifier of the process, where available |

## 2. Linux Authentication Log Analysis

### Example Log

```text
Apr  7 10:42:15 ubuntu sshd[12345]: Failed password for invalid user admin from 192.168.1.100 port 54321 ssh2
```

### Log Breakdown

| Field | Value |
|---|---|
| Timestamp | Apr 7, 10:42:15 |
| Hostname | ubuntu |
| Service | sshd |
| Process ID | 12345 |
| Event | Failed SSH authentication |
| Username | admin |
| Source IP | 192.168.1.100 |
| Source Port | 54321 |

**Security Significance:** Repeated failed authentication attempts from the same IP address may indicate brute-force activity or attempted unauthorized access. A single failed attempt is not sufficient to establish malicious intent.

## 3. Common Log Sources

### 🐧 Linux Log Sources

| Log File | Purpose |
|---|---|
| `/var/log/syslog` | General system messages on Debian-based systems |
| `/var/log/auth.log` | Authentication and authorization events |
| `/var/log/kern.log` | Kernel-related messages |
| `/var/log/apache2/access.log` | Apache HTTP access requests |
| `/var/log/apache2/error.log` | Apache errors |

*Note: Log locations vary by Linux distribution and configuration. Systems using systemd may also store logs in the system journal.*

### 🪟 Windows Log Sources

| Log Source | Purpose |
|---|---|
| Security | Logons, account changes, and security events |
| System | Operating system and service events |
| Application | Application-generated events |
| PowerShell Operational | PowerShell-related operational events |
| Windows Defender | Antivirus and threat protection events |
| Sysmon | Detailed process, network, and other system activity when configured |

**Windows Event Viewer:** Open it by running `eventvwr.msc`.

---

## 4. How SOC Analysts Use Log Analysis

- **Threat Detection:** Identify suspicious logins, unusual processes, and potentially malicious activity.
- **Incident Investigation:** Reconstruct event sequences and determine what happened.
- **Threat Hunting:** Search for indicators of compromise and abnormal behavior.
- **Security Monitoring:** Review events from endpoints, servers, and security tools.
- **Compliance:** Maintain and review records required by applicable policies and regulations.

# 6. Practical Lab — PowerShell Activity Detection

## Lab Overview

**Objective:** Generate PowerShell activity, locate the corresponding event in Windows Event Viewer, and document the available evidence.

### Requirements

- Windows 10/11 or a compatible Windows Server
- PowerShell
- Windows Event Viewer
- Administrative access to configure audit or logging policies

## Step 1 — Enable PowerShell Script Block Logging

1. Press `Win + R`.
2. Enter `gpedit.msc`.
3. Navigate to:

   `Computer Configuration → Administrative Templates → Windows Components → Windows PowerShell`

4. Open **Turn on PowerShell Script Block Logging**.
5. Set it to **Enabled** and apply the changes.
6. Open Event Viewer.

*If Group Policy Editor is unavailable, use an appropriate logging configuration for your Windows edition. Module Logging is a separate policy and is not required solely for this test.*

## Step 2 — Generate PowerShell Activity

Open PowerShell and execute:

```powershell
Get-LocalUser | Select-Object Name, Enabled
```

### Expected Result

The command displays local user accounts and their enabled status.

### Security Relevance

Account enumeration is a legitimate administrative activity. However, SOC analysts may investigate it when it occurs unexpectedly or alongside other suspicious behavior.

**Important:** Run this command only on a system you own or are authorized to administer.

## Step 3 — Locate the Event

1. Press `Win + R`.
2. Enter `eventvwr.msc`.
3. Navigate to:

   `Applications and Services Logs → Microsoft → Windows → PowerShell → Operational`

4. Select **Filter Current Log**.
5. Enter `4104` in the Event IDs field.
6. Apply the filter and inspect the available events.

### Event ID Reference

| Event ID | Meaning |
|---|---|
| 4104 | PowerShell script block logging |
| 4103 | PowerShell module logging, when configured |

**Note:** Event ID 4104 is not guaranteed to appear for every command. Logging must be configured correctly, and the generated event must contain the activity being investigated. A script block may also span multiple events.

If the expected event is missing, verify that Script Block Logging is enabled and that the PowerShell Operational log contains events for the test period.

## Step 4 — Analyze the Event

Inspect the event's **General** and **Details** tabs.

Record the following information where available:

| Field | What to Identify |
|---|---|
| Event ID | Type of event recorded |
| Time Created | When the event occurred |
| Provider | Event-generating component |
| Script Block Text | Recorded PowerShell script content |
| User/Execution Context | Account or context associated with the activity, if available |

### Investigation Questions

1. What PowerShell activity was recorded?
2. When did it occur?
3. Which script or command was logged?
4. Is the activity expected for this system?
5. What additional logs would help establish whether the activity was suspicious?

## Step 5 — Capture Evidence

Take a screenshot of the relevant Event Viewer entry.

The screenshot should show:

- The PowerShell Operational log
- Event ID 4104, if generated
- The event timestamp
- The available script block details

Do not include passwords, authentication secrets, or unrelated personal information in the screenshot.

---

## 7. Lab Conclusion

This lab demonstrates how to generate PowerShell activity and investigate the resulting Windows event records.

The exercise reinforces three core SOC skills:

1. Identifying relevant log sources.
2. Searching and interpreting event records.
3. Collecting evidence for further security investigation.

**Key Takeaway:** A log entry provides evidence of recorded activity, but context and correlation with other events are necessary to determine whether the activity is malicious.
